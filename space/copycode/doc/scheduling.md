# Планирование и оптимизация копикода emulator

`copycode.vm1.schedule` — общий хостовый планировщик копикода, MIT.
Он размещает исходные задачи по слоям, сохраняя их состав.
`copycode.vm1.optimize` — отдельный оптимизатор: преобразует копирования
и использует планировщик для размещения результата. Планировщик не импортирует
оптимизатор. Исполняемые арифметика и управление остаются копикодом.
Assembler явно выбирает режим `none`, `schedule` или `optimize`;
vm2guest использует оптимизацию по умолчанию. RV32I packing вызывает `plan`
в переходнике; конечный backend vm2 отдельно использует `optimize`.

## API и границы

- `Span(arena, lo, hi)` задаёт полуинтервал. Разные `arena` должны обозначать
  доказанно непересекающиеся области. Символические инструкции имеют отдельные
  arena до размещения; после размещения нужна проверка фактических операндов.
- `Copy(dst, src)` задаёт обычное копирование равной положительной длины.
- `Task(name, copies, fetch=(), extra_reads=(), protected=False, barrier=False)`
  задаёт неделимую группу. `fetch` описывает читаемые поля инструкции;
  после их модификации исполнение откладывается минимум на два слоя.
  `extra_reads` консервативно описывает область динамического чтения, например
  всю LUT, когда конкретный адрес выбирается патчем.
- `plan(tasks, slots)` строит детерминированное расписание раннего размещения.
  Учитывает RAW/WAR/WAW и все пересечения операндов в слое, включая src/src.
  Fan-out не бесплатен: чтения общего источника разносятся по тактам.
- `copycode.vm1.optimize.eliminate_dead_writes(tasks, live_out=None)` удаляет/укорачивает записи, перезаписанные до
  чтения. Вся память считается наблюдаемой на выходе, поэтому последнее
  присваивание не удаляется без доказанного последующего перезаписывания.
  Можно явно задать `live_out` списком Span: тогда удаляются и записи,
  не влияющие на объявленные выходы; остальные конечные биты сохранять не обещается.
- `copycode.vm1.optimize.optimize(tasks, slots, live_out=None)` повторяет удаление до неподвижной точки, планирует
  результат и сливает смежные копирования одинакового направления внутри слоя.
  Частичные записи могут разбиваться; ограничение слотов сохраняется.

`protected=True` сохраняет форму записей, на которые ссылаются патчи или
входы управления. `barrier=True` сохраняет порядок относительно всех задач
до/после барьера и останавливает анализ ненужных записей через него.
Интервалы обрабатываются целиком, без разворачивания до отдельных битов.
Расписание жадное; минимальное возможное число слоёв не гарантируется.
Нет поиска глобального оптимума, переноса между ветвями или автоматического
размножения источников. Качество зависит от порядка входных задач и барьеров.
Для RV32I на трёх холодных запусках pForth измерен выигрыш около 1,29 раза
от добавленного группирования в переходнике; конечный backend использовал
оптимизацию в обоих вариантах. Общий выигрыш 19–20 раз включает индекс словаря.
Это не оценка расстояния до оптимального расписания. Условия и исходные
результаты — [парные замеры](../../forth/doc/measurements/optimization/README.md).

Каналы не являются обычными диапазонами памяти. Вызывающий генератор должен
выделить канальные операции, переходы и неизвестные динамические доступы
в барьеры/отдельные регионы и сохранить их точную семантику. Нельзя подставлять
нулевой диапазон канала в `Copy` или выдавать неизвестный адрес за статический.
Для произвольного CFG, SYS и самомодификации без описания эффектов этот API
не делает предположений о независимости.

## Интеграция vm2

vm2guest разделяет входы управления и адреса конкретных инструкций `Ref`.
Планируются только прямолинейные регионы. Каналы, условные переходы и
копирования с неизвестными динамическими адресами остаются границами.
Для LUT объявляется вся таблица; поля патчей и fetch участвуют в зависимостях.
После размещения слои проверяет четырёхиндексный codec; независимый тестовый
аудитор проверяет фактические адреса при исполнении, включая патченные.

Это заменяет ограниченное планирование `_level` в rv32i_bulk для нового vm2.
Прямой RV32I подключает общий `plan` через `vm2compile.legacy.adapt`;
проверяются фактические операнды и семантика всех 40 инструкций RV32I.

## Проверки

`PYTHONPATH=src python3 -B tests/test_schedule.py` проверяет 2000 случайных
программ независимым побитовым эталоном всей памяти до/после планирования
и оптимизации. Отдельно проверяются RAW/WAR/WAW, src/src, лимит слотов,
fetch после патчей, барьеры, частично ненужные записи, слияние и большие
полуинтервалы без побитового расширения. Тест входит в `make check-emulator`.
Реальные проверки арифметики, динамических LUT и всех слоёв vm2 находятся
у потребителя vm2; они запускаются его `make check`.

После отделения оптимизатора проверяются также независимый импорт
планировщика и сохранение исходных объектов задач без удаления/слияния.
Прошли `make -C copycode check-emulator`, `make -C vm2 check`, проверки переходника
RV32I и oracle из самостоятельно распакованного исходного пакета copycode.
