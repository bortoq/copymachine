## Принятые решения

- legacy/ — необязательный архив. Обычные build/check/dist/run не обращаются
  к нему; его сохранность проверяется отдельно. Необходимые независимые эталоны
  принадлежат тестам активных компонентов. В активном дереве нет ссылок каталогов;
  результаты записываются по явным путям в общий build/ (пункт 12.11).

- Действующие Python/C-компоненты остаются при использующих их программах
  в `space/` до приёмки Forth-замен. Отдельный bootstrap-каталог не создаётся.
  Структура и границы: [docs/layout.md](docs/layout.md); реестр миграции:
  [docs/components.md](docs/components.md). Корневой `copy-space/` и вложенные
  архивы в активном дереве удалены; прежний проект находится в `legacy/copy-space/`.

- Проект хостового эмулятора переименован из `vm1/` в `emulator/`,
  основная команда — `emulator`. Временная ссылка `positional addressing`
  удалена после исправления обращений. Исторические ABI, Python API
  `copycode.vm1` и исходные журналы сохраняют свои идентификаторы.
- Целевая реализация проекта vm2 — Forth-скрипты трансляции адресов/копикода.
  Загрузку, выгрузку образов, trace, снимки и продолжение реализовать
  гостевыми Forth-программами через каналы/SYS. Запуск процесса, дескрипторы,
  реальные файлы и терминал обслуживает emulator; эти хостовые средства
  не относятся к транслятору. До приёмки Forth-замены Python-путь сохраняется.
- Все исходные проекты размещаются в `~/work/copymachine/`.
- По отдельному поручению пользователя создаётся общий локальный Git-репозиторий.
  Прежние истории сохраняются; публикация и новый remote не запрошены.
  Унаследованные реализации переносятся в корневой `legacy/`, переделанные
  компоненты остаются активными. Защищённый от записи корневой `.git`
  требует `.project-git` и команды `./project-git` в текущей среде.
- **Копикод** — только инструкции копирования `[n,dst,src]`.
- **emulator** — основной хостовый эмулятор. Четыре индекса
  `[dst_low,dst_high,src_low,src_high]` называются **псевдоинструкцией**;
  они описывают канал передачи сигнала между полуинтервалами источника
  и назначения. Развёрнутое объяснение — задача этапа 6.
- Обычная сборка emulator использует **bitcopy**. Двухфазный механизм адресации
  включается **при сборке через Makefile**, а не параметром запуска.
- **vm2** — пространство копикода `[n,dst,src]`. Текущая реализация —
  интерпретатор на псевдоинструкциях emulator. Целевой путь — сохраняемая трансляция
  копикода в псевдоинструкции для непосредственного исполнения emulator (этап 6).
  Прежний C-эмулятор тройки оставлен только явно вызываемым контролем и
  временным средством миграции существующих потребителей.
- Из copy-space выделяются самостоятельные проекты **rv32i**, **pforth**,
  **copy-c**, **gcc**, с собственными сборкой, тестами и документацией.
- Полезный общий копикод выделяется в проект **copycode** с модулями по назначению.
  Самостоятельные сложные реализации машин остаются в vm2 и rv32i.
- Перенос каталогов завершён. Первый этап включает пригодный к использованию
  базовый emulator с `-s/-p/-t`, каналами и stdin seed, а не только ключ сборки.
  Выделение прикладных компонентов остаётся последующей работой.

- Решение пользователя, 2026-10-20: ядро исполнения пространства — Forth,
  компилируемый прямо в индексный код (9.5–9.6). RV32I исключается из пути
  Forth и управления пространством и остаётся примером программы пространства
  и контролем. Рубеж C этапа 9 (9.7–9.9) отложен. copy-c и gcc — отдельные
  проекты, нужные для порта Linux; их выделение (этапы 10–11) отложено.
- Решение пользователя, 2026-10-20: независимые проверки разрешено запускать
  параллельно, каждую на своём ядре с прежними пределами памяти и времени.
  Замеры скорости по-прежнему выполняются последовательно на одном CPU.

Текущий сетевой механизм emulator уже **двухфазный**. Третью фазу возвращать не нужно.
Состояние адресации, число сетевых проходов и программный способ переноса битов
не являются разными наборами псевдоинструкций emulator.

## Размещение

После текущего переноса:

```text
copymachine/
  emulator/               # хостовая машина, устройства/SYS
  space/
    copycode/             # общие средства построения программ
    vm2/                  # трансляция адресов и исполнение копикода
    rv32i/                # RV32I, его генераторы и адаптация
    forth/                # pForth и действующая цепочка сборки
  tools/                  # общие команды запуска, сборки и проверки
  docs/                   # межкомпонентная документация
  build/                  # физическое хранение всех локальных результатов
  legacy/                 # единый архив выведенных из работы реализаций
  README.md, ROADMAP.md, Makefile, файлы Git
```

Целевая структура сохраняет эти корневые каталоги. По мере реализации Forth
в space/ выделяются lib/, scheduler/, optimizer/ и monitor/; до этого рабочий
код остаётся при потребителях. Новые корневые проекты и отдельный bootstrap/
не создаются. Возврат больших приложений из архива требует отдельного решения.

Это самостоятельные компоненты общего исходного репозитория.
Существующие три Git-истории и origin сохраняются локально.
При выделении новых проектов нужно сохранить происхождение файлов и лицензии;
не переписывать историю исходного copy-space. Имена удалённых репозиториев пока
не меняются. Создание общего локального репозитория запрошено отдельно;
публикация остаётся отдельным шагом.

Корневая ссылка `positional addressing` удалена при переименовании emulator;
рабочие обращения используют явные каталоги компонентов. Исторические ссылки
вне workspace не являются зависимостями активной сборки. Единственные
физические деревья проектов находятся внутри copymachine.

## Этап 6. Постоянная трансляция копикода в псевдоинструкции emulator

**Способ переноса:** пересобирать легаси из исходников и генераторов через
общее символическое представление. В `rv32i.py` уже есть `Copy`, `Field`,
`Layout` и ссылки на патченные поля — использовать их как материал для адаптера.
Канонический исходник остаётся копикодом `[n,dst,src]`; исполняемый образ
содержит готовые псевдоинструкции emulator. Полная теневая копия упакованных троек
и их интерпретация на каждом такте не являются основой нового пути.

Произвольные прежние бинарные образы, включая чтение/изменение инструкций
как нетипизированных битов, пока исполняются явно выбранным существующим
интерпретатором. Прямой путь имеет новый целевой ABI; его совместимость
проверяется на уровне объявленных операций и данных программы. Неподдерживаемый
доступ требует явной адаптации исходника или отказа сборки, без скрытого fallback.

- ✅ **6.1. Термины и границы совместимости.** Привести термины всех проектов,
  включая документацию и комментарии: копикод — `[n,dst,src]`, четыре индекса
  emulator — псевдоинструкции. Объяснить их как описание канала передачи сигнала
  в смысле теории информации, отличая его от stdin/stdout/SYS. Зафиксировать
  новый ABI прямого пути, поддерживаемые операции над кодом и отдельный
  совместимый путь; не обещать побайтовую совместимость старых образов.
- ✅ **6.2. Общие адреса и представление.** В vm2 определить трансляцию,
  целевой ABI и формат артефакта; общие примитивы сборки оставить copycode,
  специфику RV32I — будущему проекту rv32i. Ввести символы данных, слоёв,
  инструкций, логических полей `n/dst/src`, битовых срезов и релокаций.
  Адреса и ширины вычислять после планирования и размещения; убрать из

  и заданий; физические адреса контейнера и встроенные ссылки пересобирать.
- ✅ **6.3. Проверочный прототип до полного переноса.** На минимальном общем

  копирования `[n,dst,src]` → `[dst,dst+n,src,src+n]` с проверкой границ,
  NOP и переполнений. Один общий backend должен размещать символы, выпускать

## ❌ Этап 9. Базовая среда Forth и программы пространства на Forth

**Цель:** на Forth можно написать, собрать и выполнить произвольную программу
в пределах доступной памяти и документированных устройств пространства,
включая собственные средства разработки. Это требует полноценной среды,
а не только вычислительной полноты языка. Компиляция пользовательской программы
и работа инструментов выполняются внутри пространства; хост предоставляет
emulator и согласованный ввод/вывод. Существующий pForth/RV32I служит начальной средой.

**Стратегия.** Основной путь Forth-кода — прямая компиляция в индексный код
emulator, без промежуточного RV32I. Порядок величин после 8.8: Forth-примитив
на универсальном RV32I стоит 4–8 тыс. тактов, через статический транслятор
RV32I — около 0,6–1,2 тыс., при прямой компиляции ожидается 30–100
(оценка; её проверяет спайк 9.5.1). RV32I исключён из пути Forth: транслятор
RV32I нужен только для чужого машинного кода и отложен вместе с рубежом C. Оба пути используют один бэкенд
на Forth (9.4): построение слоёв и загрузочного потока, таблицы, общие
обработчики с вызовом и возвратом через патч, проверки адресов и откат.
Поэтому сначала бэкенд, затем прямой компилятор и ядро Forth, затем перенос
транслятора RV32I на тот же бэкенд.

**Рубеж A — среда и бэкенд (9.1–9.4):** контракт и проверка имеющихся слов,
память, ошибки, ввод/вывод, средства построения индексного кода на Forth.
**Рубеж B — прямой Forth (9.5–9.6):** компилятор Forth в индексный код и
собственное ядро. **Рубеж C — машинный код (9.7–9.9), отложен:** транслятор и эмулятор
RV32I, vm2 на Forth. Переписывание большого прикладного кода copy-c, GCC/newlib
и Linux отложено; оно не блокирует приёмку рубежей. Сначала использовать
небольшие независимые программы.

## ✅ Этап 13. Подготовительные исследования к language (исполнение субагентами)

Дата: 2026-10-22. Готовит данные для перехода с Форта на язык language
и с SYS на хост пространство. Решения по языку принимает автор; этот этап
только исследует и строит прототипы. Рабочий путь (make, tools/run/forth,
выпуски) не меняется. Пункты описаны самодостаточно: субагенту не нужно
выяснять задачу самому.

**Краткий контекст для всех пунктов.** Язык language заменит Форт. Слово
делится на понятие (имя + эталонные артефакты) и определение (заменяемый код).
Артефакт — результат исполнения на битах, прочитанных через канал. Определение
заменяется, если артефакты всех затронутых слов совпали, точность не ниже,
а цена меньше. Цена — функция числа скопированных битов, копирований и слоёв.
Минимальный набор слов: копирование, канал; таблица, последовательность,
повторение; создать понятие, связать с определением, синоним; проверка, цена,
бюджет, замена определения. Ветвление — через таблицу и копирование по
вычисленному полю. Требование: начальных механизмов должно хватать, чтобы
заменить само определение «слово». Термины: хост, гест, инструкция, поле
инструкции, канал (не «вход»). Машина рассуждений — копимашина (vm2,
инструкция из трёх полей `[n,dst,src]`).

## ✅ Этап 14. Эксперимент: язык language по новому определению языка

Дата: 2026-10-25. Основание — разделы 1, 2.1, 2.2, 2.9–2.11 файла обсуждения
дизайна (`exclude_this_file_from_git.txt`). Эксперимент: построить язык,
определение которого написано только его словами, бут компилирует это
определение в инструкции индексного пространства, а слово языка имеет
механизмы понятия, определения, цены, типа адресации и доказательства.
Рабочий путь (ядро K в `space/forth`, make, выпуски) не меняется: язык
строится отдельным компонентом `space/language/` из копии исходников K.

**Краткий контекст для всех пунктов.** Язык language заменит Форт. Слово
языка — механизм; его части и механизмы тоже слова. Понятие: имя,
эталонные артефакты, ячейка понятия (позиция, через которую вызывается
определение). Определение: код, воспроизводящий артефакты; заменяемо;
у определения есть тип адресации (копи-, индекс-, хост пространство; сейчас
реализуется только индексное). Артефакт — результат исполнения на битах,
прочитанных через канал. Ядро языка — слова, использованные в определении
языка; определение языка не содержит ничего, кроме слов языка (замкнуто).
Основание — копирования: определение инструкции — она сама. Компиляция —
преобразование определения на языке в определение на инструкциях
пространства. Бут — компиляция определения языка; первый раз её выполняет
хостовой 32-битный pForth, исполняющий тот же текст определения (другой
исполнитель того же определения), дальше — сам язык. Примитивы — слова-
генераторы: слово словаря, исполняемое при компиляции и выдающее копикод
(как `IMMEDIATE`). Литералы — полуинтервалы позиций с постоянными битами,
цифры — синонимы литералов, числа — слова. Цена — биты, копирования, слои
и размер определения; слово `PRICE` сводит их в одно число (заменяемо).
Доказательство — полная проверка; у доказанного слова механизм
доказательства — ссылка на общее слово «доказано» (таблица из одного
однобитного значения 1). Новое определение проверяет старое (рабочее)
слово; замена — если точность не ниже, а цена меньше; прежнее определение —
в стек определений. Синоним — имя на ячейку понятия исходного слова: та же
цена. Ядро изолировано: программа пользователя не пишет, не читает и не
исполняет ядро иначе, чем вызовом слова. Термины: хост, гест, инструкция,
поле инструкции, канал (не «вход»).

## ❌ Этап 18. Общий компьютер и бут без pForth

- Цель: одна вычислительная система, где любое вычисление — копирования

  пользователей (возможно, торговля определениями) или пространство,

## ❌ Этап 23. Улучшение языка

Решение автора 2026-11-04: разделить язык на вложенные языки, чтобы
упростить программирование и уменьшить число слов. Разметка старого кома
(23.0) показала, что он не делится: определение написано сверху вниз на
одном большом Форте (нижние языки описаны верхним). Поэтому языки строятся
заново снизу вверх; нынешний язык не трогается, пока новая цепочка не
догонит его.

Источники (2026-11-04): stage0 / bootstrappable builds — цепочка крошечных
языков, каждый — программа на предыдущем, от 181-байтового зерна hex0
(<https://bootstrapping.miraheze.org/wiki/Stage0>,
<https://github.com/oriansj/stage0-posix>); nanopass — много проходов, у
каждого промежуточного языка грамматика, проверку делает грамматика, а не
код (<https://gwern.net/doc/cs/lisp/2005-sarkar.pdf>,
<https://www.cs.tufts.edu/~nr/cs257/archive/icfp13.pdf>); transport-triggered
architecture и машины одной команды MOVE — вычисление как пересылка,
арифметика таблицами (<https://en.wikipedia.org/wiki/Transport_triggered_architecture>);
sectorforth — Форт из 8 примитивов (<https://github.com/cesarblum/sectorforth/>);
COLA, Piumarta — самоописание снизу (<https://piumarta.com/software/cola>);
Amin, Rompf, «Collapsing towers of interpreters», POPL 2018 — башня
интерпретаторов схлопывается в один проход компиляции
(<https://www.cs.purdue.edu/~rompf/papers/amin-popl18.pdf>).

Решение автора 2026-11-04 (журнал дизайна 7.2.31): язык копимашины —
несколько строго вложенных языков; каждый работает в своём пространстве и
сам — компилятор в пространство предыдущего. 1-й — одно слово: копия по 4
индексам (индекспространство); 2-й — 3 аргумента (длина, куда, откуда),
экономит ~1/4 пространства (копипространство); 3-й — таблицы (лут);
дальше — длинное, экономное (цена), ..., дальнее. Изоляция — непересечение

## ❌ Этап 19. Пространство хоста на голом железе (отложено)

**Отложено.** Работа требует уточнения и тщательной проработки плана
выполнения до старта (Стоп для автора): какой вариант (эмулятор вместо
`init` или код эмуляции внутри ядра), какие устройства нужны первыми,
какая версия Linux, как проверять на железе. Ниже — набросок и оценка
2026-11-04, а не план.

- **Цель:** взять исходники Linux, выбросить всё, что не нужно для
  адресации хоста (все устройства доступны как одно битовое пространство,
  журнал дизайна 7.2.30), добавить в эти исходники код эмуляции
  пространства и проверить, что такое пространство запускается на голом
  железе.
- **Набросок шагов и оценка (исполнителями):**
  1. Урезанное ядро: от `tinyconfig` + накопители (NVMe, SATA, USB),
     клавиатура, консоль; без сети — 0,5–1 день.
  2. Эмулятор (статически) вместо `init`; все блочные и символьные
     устройства — области пространства хоста без `-r path`; проверка в
     QEMU — 0,5 дня.
  3. Код эмуляции внутри ядра (встроенный модуль, поток ядра, память и
     устройства через API ядра) — 3–6 дней, самый рискованный.
  4. Физически выбросить из исходников неиспользуемое по итогам сборки —
     1 день.
  5. Голое железо: QEMU/KVM, затем загрузочный образ на флешке; запуск
     на машине — автор — 2–3 ч и исправления.
  Кратчайший путь (1, 2, 5) — 1,5–2 дня; полный (1–5) — 5–9 рабочих дней,
  разброс ×1,5.
- **Нужно на машине:** `flex`, `bison`, `libelf-dev`, `libssl-dev`,
  `musl-tools` (ставит автор).
- **Зависит:** 18.25, 18.26 (длинные копирования доделаны).
