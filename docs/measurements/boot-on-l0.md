# Бут и тесты на L0 вместо pForth: замер (18.2)

Дата 2026-10-30, машина: Linux 6.2 x86_64, 12 ядер. Код проекта не менялся; временные сборки эмулятора
(счётчики, профиль, быстрый `space_get`) — вне репозитория. Цифры «ticks» детерминированы, секунды — на
одном процессе, если не сказано иное. Опорные цифры: `docs/measurements/check-full.json`.

## 1. Кто использует pForth (`tools/host.py`)

`host.build()` вызывают 14 файлов (в задаче «13»: `word_cost.py` и `user_programs.py` считаются инструментами).
Компиляций программ на хосте в файле — по `grep` вызовов `compile_on_host/compile_language/run_host/
compile_with_records` (порядок величины, не точный счёт).

Итог. Без компиляции, по модели, можно сверять: бут, потоки `check-programs`/`check-kernel`/`check-space-replace`,
`test_comments`, часть `test_literals` — это 6 из 14 файлов и почти все 37-кратные компиляции.
Остальные 8 используют слова языка (`cost`, `price`, `check-table`, `replace`, `host`, `long!`), которых в `model.py`
нет, и записи словаря (`word_cost.py`). Их программы можно компилировать самим L0 (так уже делают `test_isolation`
и `check-kernel`), но это стоит секунды-минуты на программу (п. 2).

Скорость: модель — 4,4 с на весь язык (pForth: `make boot` 11,7 с, из них 3,9 с пользовательских и 6,1 с
системных; вероятно, вывод L0 побайтно — не проверялось); 37 программ: модель 1,4 с, pForth 8,6 с (измерено в одном процессе Python,
сравнение потоков: 37/37 равны).

## 2. Где эмулятор тратит время на L0

Метод: программа `arithmetic` (79 символов) и остальные 36 из `forthc_programs.py` подаются так же, как в
`check_kernel.py`: stdin = L0 + текст + `\0`, ключи `-s 2^31 -p 8`. Эмулятор пересобран вне репозитория: с
`gprof -pg -fno-inline`, со счётчиками (число активных ячеек слоя за такт, длины копий), с гистограммой «слой
по адресу следующего слоя» (адрес источника строки связи, слот 7; адрес / 1024 -> ячейка) и склейкой с
записями словаря `word_cost.definition()` (имя, ячейка входа, размер в ячейках).

### Такт

| Величина | Значение |
|---|---|
| тактов на компиляцию `arithmetic` | 30 412 534 (9,0 с, 296 нс/такт) |
| минимум на программу (28 символов) | 20,3 млн тактов: фиксированный разбег компилятора (22,5 % всех тактов `check-kernel`) |
| 37 программ всего | 3 339 млн тактов -> 988 с на 296 нс; `check-kernel` = 1047 с (остальное — pForth, 2 пробы) |
| бит скопировано за такт | 1042 (31,7 Гбит за 30,4 млн тактов), из них одно копирование строки связи (1024 бита) на каждый такт |
| активных строк за такт (из 8) | в среднем 2,86 (35,7 %); без строки связи 1,86 рабочих из 7 (26,6 %) |
| распределение активных (1..8) | 21,3 / 23,6 / 31,7 / 13,4 / 2,4 / 0,4 / 2,6 / 4,5 % тактов |
| gprof (`-fno-inline`) | `space_get` 78 % (32 вызова на такт: 8 строк x 4 поля побайтно), `computation` 8 %, `sys_tick` 5 %, `bitcpy` 4 %, `backend_tick` 3 % |

Заполненность: полный слой (7 рабочих строк) — 4,5 % тактов; слои с 7 из 8 — 2,6 %. Следовательно, «не хватило
мест в слое» (то, что лечит более широкий процессор) — не более 7 % тактов, остальные такты ждут зависимостей
(цепочки слов). Ключ `-p`: ядро L0 собрано с ячейкой слоя 8 строк (`-p 8`, строка связи + 7 рабочих), и компилятор
не допускает больше (`cc-machine`: `slots > 8` -> `-24`), поэтому `-p 16` на этом L0 не запускается (прогон с
`-p 16/64` не завершился за 40 с: слой в памяти другой). Оценка выгоды более широкого процессора:
не более ~7 % тактов, при этом каждый такт станет дороже (раскодирование всех строк слоя). Решение 5.2.2
(«увеличить, если ускорит») по заполненности не оправдано: ускорение даёт не ширина, а цена такта и число тактов.

### Предел скорости такта

Тот же эмулятор с одной правкой `space_get` (быстрый путь для поля 32 бита по границе байта: четыре байта через
таблицу разворота битов вместо побайтного цикла со сдвигами), выход побайтно тот же:

| Сборка | arithmetic, 30,4 млн тактов | на такт |
|---|---|---|
| исходная, `-O2` | 9,05 с | 296 нс |
| быстрый `space_get`, `-O2` | 4,22 с | 139 нс |
| то же + PGO (обучение на этой же программе) | 3,86 с | 127 нс |
| то же, `-O3 -march=native` | 5,08 с | (без выигрыша, шум) |

Нижняя оценка по копированию данных: 3,96 Гбайт за прогон при ~10 Гбайт/с — 0,4 с, то есть предел ~15–30 нс на
такт (оценка, не измерение): ещё в 4–8 раз над быстрым путём, но потребует переписывания `computation` целиком.
Практический выигрыш правки — 2,1x на одной строке.

Параллельность: 12 ядер, но эмулятор делает по 4 Гбайт копий на программу и упирается в память:
37 программ в 11 процессов — суммарное время процессов 2633 с против 988 с в одиночку (рост такта до ~880 нс);
стена параллельного прогона 37 программ: 275 с (исходный эмулятор, 11 процессов; в одиночку ~990 с),
134 с (быстрый, 11 процессов; в одиночку ~470 с по тактам), 139 с (быстрый, 6 процессов: упор в самую долгую программу и в память). Ускорение от
параллельности ~3,5x, а не 11x: память. `check-kernel` последовательный: 1047 с.

### Профиль по словам языка (гистограмма ячеек x записи словаря)

Три прогона: (A) малая программа (20,3 млн тактов), (B) программа с `*` (243,9 млн), (C) первые 4 млрд тактов
`check-self` (L0 компилирует собственный источник, 20 % всего прогона; 5732 с = ~19,4 млрд тактов по 296 нс).
«Вход» — число входов в первый слой слова.

| Слово | A, % | B (`multiply`), % | C (check-self, начало), % | Что делает |
|---|---|---|---|---|
| `cc-numeric4` (+ `cc-field-check`, `cc-encode`, `cc-numeric`, `cc-encode-layer`) | 4,5 (+0,8 + 4,3 + 5,0) | 5,7 (+1,1 + 5,4 + 1,7) | 16,4 (+3,0 + 15,5 + 0,5) = **35,5** | запись слоя в байты: 32 поля x побайтно через таблицу `cc-rev` |
| `fill` | 29,4 | 7,0 | 13,6 | обнуление буферов циклом по байту (`cc-dest @ cc-lbytes 0 fill` — на каждый слой) |
| `kn-put` | 19,2 | 4,7 | 9,0 | приёмник байтов в пространство ядра: цикл `space!` / `spacec!` |
| `+!` | 9,6 | 3,2 | 6,0 | `dup >r @ + r> !`, вызывается 2,7 млн раз |
| `cmove` | 1,9 | 3,4 | 4,4 | копирование циклом по байту |
| `cc-clash?` + `cc-row-clash?` (+ `cc-clashes?`, `cc-row-set`...) | 0,9 + 0,6 | **22,1 + 13,9** | 5,4 + 3,4 (13,6 вместе с `2@`, `cc-count`, `cc-row`...) | проверка пересечения новой строки с уже стоящими в слое |
| `cc-table` + `fc-off-table` | 4,0 + 5,0 | 0,8 + 0,4 | — | таблицы при запуске (фиксированный разбег) |
| префикс `fc-` вместе (читатель, словарь, ссылки) | — | — | 7,9 | фронтенд компилятора |
| префикс `cc-` вместе | — | — | 53,7 | бэкенд: слои и строки |

Сводка по C: слой в индексном коде записывается ~72 тыс. тактов (55 590 слоёв за 4 млрд тактов): слова
**запись слоя в байты (35,5 %)**, **заполнение/копирование/`+!`/`kn-put` (33,1 %)** и **проверка пересечения строк
(13,6 %)** — вместе 82 % тактов. Фронтенд (чтение, поиск слов, словарь) — 8 %, ещё около 7 % — служебные
слова (`?dup`, `2@`, `cc-count`...). Программы с `*` и `/` (9 из 37: `multiply`, `divide`, `modulo`, `mul-random`,
`divmod-random`, `mod-signs`, `faults`, `loop-sum`, `uncaught-zero`) строят вспомогательные подпрограммы
(планировщик слоёв, `compute.fth`): 2157 млн из 3339 млн тактов `check-kernel` (65 %), у них доминируют
`cc-clash?` / `cc-row-clash?` (36 % тактов программы `multiply`).

Цена слов в языке (`word_cost`) относится к исполнению слова в пространстве, а не к компиляции им; она не
использована. Счётчики 13.4 (`counters.py`) работают на одной программе по 1000 тактов без профиля по словам;
профиль по словам получен по гистограмме ячеек.

Что дало бы переписывание этих слов (оценка по проценту тактов, не измерение; текст определения тот же для
pForth и L0, поток L0 проверяется `K0 == L0`): `fill` обнуляющий буфер — одно копирование нулей длиной в буфер
вместо цикла (идея: на машине копирования это один такт); запись слоя прямыми `!` полей, когда `cc-rev` —
тождество (в ядре так и есть, `kn-order`), вместо побайтной таблицы; проверка пересечения на значениях в
регистрах без `variable`-ов. Если эти шесть групп станут в 3–5 раз дешевле, число тактов `check-self` упадёт
в 2,5–3 раза.

## 4. Путь автора: долгие определения на хосте

### (а) Перенос отдельных определений при нынешней цене вызова

Цена вызова `host`: программа `c` (`15 and`) в гесте 118 мкс, в хосте 2,17 мс (±0,19), то есть накладные
расходы вызова 2,1 мс; долгое слово `g` (300 раз `dup 7 * xor`) 9,93 мс в гесте и 2,18 мс на хосте
(выигрыш 4,6x, всё время — вызов). Измерено словом `time` (наименьшее из 7 прогонов) на программе, собранной
pForth, исполнителем — исходный эмулятор. Окупается слово дороже ~2,2 мс = ~7,4 тыс. тактов за вызов.

Слова компилятора по среднему числу тактов за вход (профиль B/C): `cc-encode` ~11 тыс. тактов (3,3 мс),
`cc-numeric4` 370 тактов (0,11 мс), `cc-clash?` ~500 (0,15 мс), `fill` ~4,7 тыс., `kn-put` ~6,5 тыс. (профиль C,
такты / входы). Выше порога только `cc-encode`; `kn-put` и `fill` около него, а `host` берёт лишь ( x -- r ) из 13 слов без памяти и без циклов,
а эти слова работают с памятью, переменными и циклами. Допустимых слов в компиляторе, по сути, нет: **выигрыш (а)
по компилятору — ноль**, а как проба механизма `host` — есть (4,6x на чистом арифметическом слове).

### (б) `host` до всего определения компилятора

Что есть: `gen-host` (`primitives.fth`, ~40 строк) переводит слово в короткую программу C на стековой машине
(`switch` по номерам операций, стек `unsigned s[300]`), 13 слов, числа; вызов — процесс + файл.

Что нужно: перевести ~450 двоеточий (определений `:` по файлам: `forthc` 210, `primitives` 95, `backend` 54, `compute` 52, `prelude` 30, `kernel` 5, `main` 3), 58
внешних имён ядра (память, переменные, `create/allot`, `@ ! c@ c! cmove fill`, управление `if/else/begin/while/
repeat/do/loop/?do/leave/unloop/recurse/exit`, возвратный стек `>r r> r@`, `execute`, `catch/throw`, `key/emit/type`,
`allocate/free` пула, 2-ячеечные `2@ 2!`, строки `s"`), генераторы (`primitives.fth`), которые на хосте исполняет
сам компилятор — их нужно перевести тоже (иначе C исполняет только слова, а не расширение словаря в
исполнении). Это второй «Форт» на C: стек данных и возвратный как массивы, слова — функции C, память —
массив байт, ввод/вывод — `stdin/stdout`.

Объём работы (оценка Sonnet-этапами, по числу независимо проверяемых частей; проверка — тот же поток L0 побайтно):

| Часть | Этапов |
|---|---|
| память пространства (`@ ! c@ c! cmove fill`), переменные, `create/allot/constant`, строки | 1 |
| управление, циклы, возвратный стек, `recurse`, `execute`, `catch/throw` (xt, `cc-sink`, `cc-on-write`) | 1–2 |
| ввод-вывод (`key`, `emit`, `type`), `allocate/free`, генераторы (определяющие слова, `fc-eval`), замыкание на 58 внешних имён | 1–2 |
| сборка: `make boot` = `cc` над C-семенем; генерация семени самим языком на L0 и сверка C-текста; `check-closure`/документы | 1–2 |
| итого | 4–7 этапов, по порядку работ от двух недель до месяца (оценка) |

Ожидаемая скорость `make boot` (оценка из измеренного): pForth считает 100 млн итераций `0 do i 1+ drop loop` за
1,98 с (~5 нс на операцию), его бут — 3,9 с пользовательских и 6,1 с системных;
C -O2 даёт ~1 нс на операцию и буферизованный вывод: компиляция языка 0,3–0,8 с; сам `cc` на ~25 тыс.
операторов — 2–5 с. Вместе `make boot` 3–6 с (против 11,7 с pForth, 4,4 с модели). Семя C кладётся в репозиторий
(как сегодня зерно L0); обновление семени — язык на L0 переводит свой текст в C: фронтенд (чтение, словарь)
8 % + служебные слова ~10 % тактов компиляции = около 3,5 млрд тактов: ~17 мин на исходном эмуляторе, ~8 мин на
быстром (оценка по профилю C), вместо 1,5 ч `check-self`.

Время для A, B — из измерений: A — 2,1x/2,3x на одном прогоне; B — 82 % тактов в шести группах слов при
ускорении группы в 3–5 раз даёт 2,2–2,9x по тактам (оценка), поверх A.

## Рекомендация

1. Сразу (недели не нужны): A и C — 2 этапа, ускоряют `check-kernel` с 17 минут до ~2 (134 с измерено на быстром эмуляторе в 11 процессов), не вводят механизмов.
   Эмулятор — определение слова «пространство»; правка `space_get` проверяется его же тестами.
2. Затем B — точечное переписывание слов компилятора в профильном порядке; это единственное, что уменьшает
   `check-self` (одна цепочка не параллелится). Потолок ~10–15 минут вместо 1,5 часа; тест `K0 == L0` страхует
   каждый шаг.
3. D даёт «pForth удалён» дёшево для бута и потоков; E нужен, если автор хочет, чтобы `make boot` был быстрым без
   модели (Python): 3–6 с. Рекомендую D сначала, E — по решению автора после B (его выигрыш — только независимость
   от Python-модели и 3–6 с против 4,4 с).
4. Широкий процессор (`-p`, решение 5.2.2) не оправдан замером: полные слои — 4,5 % тактов; компилятор допускает
   слой не больше 8 строк.
5. Перенос отдельных определений на хост (а) при цене вызова 2,1 мс не окупается для слов компилятора (память,
   циклы, малые тела); есть смысл только для чистой арифметики.

## Как воспроизвести

- Эмулятор с счётчиками/гистограммой: копия `emulator/src` вне репозитория; в `computation` добавлены гистограмма
  числа активных строк, длин копий, гистограмма `instructions[proc_n-1][2] >> 10`; ячейки сопоставляются
  с `word_cost.definition()` (`entry / 1024`, `size`).
- Ввод `check-kernel`: `L0 + текст программы + \0` на stdin эмулятора с `-s 2147483648 -p 8`.
- Профиль `check-self`: stdin = `L0 + COMPILER_FILES + \0 + KERNEL_FILES`, `-t 4000000000`.
- Вызов хоста: программа с `: c-host host c ;` и `time`, собранная pForth, `-r host.c -r host.io`.
