# Башня языков: разметка слов ядра (21.1)

Разбор, код и документы не менялись. Скрипт: `language-tower-tools/classify.py` (правила явно: имена `NAMES`, `GEN`, диапазоны строк `RANGES`); полный список слов с группой, способом разметки, ячейками и «кого использует» — `language-tower-tools/words.tsv`. Воспроизведение: `(cd language/tools; LANGUAGE_OUT=/tmp/x python3 word_cost.py > /tmp/wc.txt)`, затем `python3 -B classify.py --cost /tmp/wc.txt --tsv words.tsv`.

## 1. Что размечено

Источник — тот же граф, что даёт `language/doc/core.md` (`check_closure.core_nodes`, он использует `defgraph.py`): **995 узлов = 992 имени** (3 имени определены дважды: `lay-l1`, `lay-l2`, `fc-code`…) **= 982 слова + 10 цифр**. Виды: `:` 486, переменная 329, генератор 71, `create` 63, константа 29, цифра 10, основание 6 (основание — те же `:`).
Способ: 475 узлов размечены руками (по имени), 441 — по диапазону строк файла, 69 имён-генераторов (`+`, `dup`, `if`…) наследуют группу своего компилятора `gen-*`, 10 цифр — LIT. Неразмеченных нет (UNK 0), но спорных много — §4.

## 3. Предлагаемая принадлежность групп

| Группа | Предложение | Основание |
|---|---|---|
| ENC | «компилятор L1 → L0» (формат потока) | пишет ячейки/слои в поток эмулятора; `lay-rev` — тождество в ядре |
| SCH | «компилятор L2 → L1» | раскладывает строки по слоям так, чтобы они не пересекались (`3.7.2`); два планировщика (см. §6) |
| PRF | инструмент над L1 (проверка образа), не язык | читает слои из пространства (`dj-reader`); если L2→L1 строит непересечение по построению, нужен только для чужого L1 |
| GRD | свойство компилятора Форта → L3 | маска младших бит адресов; при изоляции пространствами не нужна |
| CAL, CTL, STK, MEM, LIT, TXT, DRV | «компилятор Форта → L3» (отдельный язык поверх L3, вопрос 1) | их единственная цель — выдать L3-код слов Форта |
| DIA | L4 (stdout — канал хоста) + диагностика компилятора | `fc-reject` печатает через `type` и останавливает хост |
| HF | вне башни: слова pForth, на которых работает хост-компилятор | `prelude.fth` не грузится в образ как язык |
| LAY | L2 (копипространство: где что лежит) | константы смещений регионов |
| L5p / L5r / L5h | три подмножества L5: цена, замена, хост/платформы | как в наброске автора |

## 4. Спорные слова (разметка руками)

| Слово | Выбрано | Почему спорно |
|---|---|---|
| `lay-copy` | L2 | единственное слово с 3 аргументами; но тело в основании, на нём построен и L1 (`lay-row` 4 индекса) |
| `lay-row` | L1 | основание, но вызывает планировщик (§5, пункт 4) |
| `space!/@`, `fc-space-*`, `fc-stx…` | L3 | вычисляемая позиция: сумматор + правка полей строки — это L2-копия с патчем или L3? |
| `fc-key`, `fc-read-key`, `emit`, `key` | L4 | канал stdin/stdout — вещь хоста; но `lay-stdin/stdout` есть и в L1 (строки канала) |
| `fc-cp`, `fc-copy-row` (`%COPY`) | L4 | это 4-индексная копия L1 для программы, но разрешена только с long |
| `fc-forbidden`, `fc-num` | L4 | цена `fc-forbid` — L5, использование — L4 |
| `lay-on-write` | L5p | хук в записи слоя ENC, нужен только цене |
| `fc-rt`, `fc-rta`, `fc-concept-record` | L5r | таблица замен лежит в каждой записи слова |
| `fc-eval`, `fc-library` | L5h | текст компилируется «посреди канала», вызывается из `fc-long*` |
| `fc-mechanisms`, `fc-proved*` | PRF | доказательство по таблице или проверка слова — не `dj-*` |
| `gen-cells`, `gen-cell+`, `gen-2*` | L3 | по сути сдвиг/константа; могли бы быть L2 |
| `fc-sga…fc-sfinish` (323–388) | SCH | в тех же строках есть арифметика (`negate-chain`) — отнесена к L3 диапазоном 374–388 |
| `fc-off*`, `fc-t-*` | L3 | таблицы на старте; часть (`fc-t-bytepos`) нужна только MEM |

## 5. Нарушения вложенности

Граф: ребро A → B, если определение A называет B (`defgraph`, тот же что в `core.md`). Ранги: L1 < L2 < L3 < L4 < L5; ENC, PRF — ранг 1, SCH — 2, слой Форта и GRD — 3; DIA, HF, LAY вне порядка.

**А. Системное.** Всё определение написано на Форте (самоприменимо): слова L1, ENC, SCH, PRF используют имена-операторы Форта (`+ and cells dup @ if do loop`), которые по смыслу L3 / слой Форта. Это не случайные нарушения, а способ написания: нижний язык описан верхним.

| Группа (`:`-слов) | `:`-слов, использующих операторы Форта | Операторов (число разных): арифметика L3 / стек / память / управление |
|---|---|---|
| L1 (24) | 23 | 14 / 9 / 2 / 6 |
| SCH (17) | 17 | 15 / 10 / 2 / 13 |
| ENC (18) | 18 | 16 / 9 / 4 / 11 |
| PRF (30) | 29 | 13 / 8 / 2 / 7 (+ `execute`) |
| L2 `lay-copy` | да | `+`, `1-`, `lshift`, стек, `if` |
| L3 (105) | 98 | сами себя: `lay-adder` и пр. написаны на Форте, их «значения» готовы только после компиляции |

Следствие: L1 и L2 нельзя определить сами на себе: чтобы вычислить `hi = lo + n`, нужен сумматор, а он — L3-таблица. Это вопрос 2.

**Б. Настоящие инверсии между подсистемами** (без операторов Форта; кроме `PRF → L4`, нижний знает о верхнем):

| От → к | Рёбер / слов | Слова (примеры) | Причина |
|---|---|---|---|
| TXT → L5p | 17 / 7 | `fc-init`, `fc-words` → `fc-log fc-calls fc-pend fc-decs`, `fc-plit fc-ll` | журнал цены заводится и сбрасывается разбором текста |
| LIT → L5p | 10 / 5 | `fc-literal`, `fc-lit?`, `fc-mul-lit?`, `fc-pick-roll` → `fc-ll fc-llr fc-llv fc-plit` | «последний литерал» помнится ради цены пути |
| CAL → L5p | 9 / 4 | `fc-call`, `gen-call` → `fc-log-call`, `fc-plit` | запись вызова в журнал цены |
| L4 → L5p | 8 / 2 | `fc-forbidden`, `fc-num` → `fc-forbid fc-cost! fc-plit` | цена long = fc-forbid задана внутри L4 |
| CTL → L5p | 5 / 5 | `fc-branch`, `gen-begin/do/?do/recurse` → `fc-log-decision`, `fc-by-execution` | отметка «цена по исполнению» |
| L3 → L5p | 4 / 2 | `fc-build-div`, `fc-call-helper` → `fc-log-*`, `fc-mul-cost`, `fc-div-cost` | цена помощников `*` `/` |
| DRV → L5p / L5h / L4 | 3+1+1 / 1 | `fc-compile` → `fc-log-begin/end`, `fc-helpers-cost`, `fc-library`, `fc-long` | драйвер компилятора (ему можно: он выше) |
| ENC → L5p | 1 / 1 | `lay-write` → `lay-on-write` | хук в записи слоя |
| TXT → L5r | 4 / 3 | `gen-colon`, `gen-semicolon`, `fc-init` → `fc-rt`, `fc-concept-record` | запись слова всегда несёт таблицу замен |
| CAL → L5r | 1 / 1 | `fc-concept` → `fc-rta` | ячейка-понятие несёт замену |
| L4 → L5h | 3 / 3 | `fc-long`, `fc-long-host`, `fc-long-kernel` → `fc-eval` | текст в середине канала |
| TXT → L5h, L4 | 2+2 / 1 | `fc-generators` → `gen-host gen-library gen-emit gen-key` | реестр генераторов знает все языки (допустимо: реестр) |
| L1 → SCH | 4 / 1 | `lay-row` → `lay-new-row lay-full? lay-row-set lay-clashes?` | основание «строка» содержит планировщик |
| PRF → L4 | 5 / 2 | `dj-prove`, `dj-head?` → `lay-req/rec/hdr/cap` | доказательство знает раскладку запроса long |
| PRF → TXT, LIT, L5p | 3 / 2 | `fc-proved?` → `fc-word-of`; `gen-proved?` → `fc-literal`, `fc-known-xt` | `proved?` — слово словаря, не `dj-*` |
| SCH → STK | 1 / 1 | `fc-place` → `fc-4@` | кэш регистров читается планировщиком |

Главная инверсия — **цена (L5p) вшита в нижние**: 24 слова вне L5p вызывают хуки цены (`fc-log-*`, `fc-pl*`, `fc-by-execution`, `lay-on-write`). Если L5 — компилятор в L4, цену надо считать по слоям уже готового кода (`lay-on-write` как раз это и делает), а не отмечать при разборе.

**Никуда не ложатся** (после правил — 0), но слабо: `fc-key` (бит для KEY среди регистров), `fc-ck…fc-cbk` (хеш констант), `fc-htab` (хеш словаря), `fc-off*` (14 таблиц смещений, нужны только MEM), `fc-ring/window` (кольцо планировщика), `HF` (29 слов pForth), `DIA`, `LAY`, `DRV`: «хозяйство» компилятора, у которого нет языка-хозяина (вопрос 3).

## 6. Наблюдения

1. **L2 в ядре почти не выделен.** Слов, которые мы бы назвали «инструкцией из 3 аргументов», одно (`lay-copy`); остальное из L2 (где лежит приёмник, сумма `lo+n`, раскладка регионов) растворено в L3 (сумматор, 16 слов L3 зовут `lay-copy`) и в SCH. Четверть экономии пространства (7.2.31) не видна в словах ядра: размещение строк — в `lay-row` (L1) и `fc-place` (SCH).
2. **Два планировщика**: `lay-clash?…lay-fits?` в `lay-row` и прямолинейный `fc-ring/fc-place/fc-slookup` (323–388, 5 473 ячейки вместе). Один из них лишний, если расписание строится в L2→L1.
3. **Проверки, которые уберёт разделение.** (а) `dj-*`: 71 слово, 10 578 ячеек (9,4%) — доказательство непересечения L1-образа; при компиляции L2→L1 по построению нужно только для постороннего L1. (б) `fc-guard`: 19 слов читают его (6 251 ячейка, 5,6%: `fc-ret*`, `fc-xt*`, `space-end`, `fc-long`), плюс `fc-check`/`fc-chk-*` — маска младших бит на каждый доступ к памяти и вход/возврат; изоляция «непересечением данных» заменяет маску раскладкой пространств. (в) `fc-reject`: 47 слов проверяют ёмкость/неизвестное слово (−8, −13, −22, −16); они стоят на пути слов нижних языков, где ошибок быть не должно (по 18.24 «ошибок нет»), их 16 597 ячеек (14,8%) включают весь код слов, где стоит проверка, а не только саму проверку. (г) `lay-field-check`, `-24/-9` в ENC.
4. **Размер языков.** L1 — 52 слова (23 переменные состояния слоя), 2 203 ячейки; L3 — 265 слов и 26% кода, но из них 138 — рабочие переменные/данные компилятора (адаптеры `lay-a*`, `lay-d*`, `lay-t*`): сами функции таблиц малы (≈ 25 слов `*-entry`, по 40–500 ячеек), основное — построители `fc-build-mul/div` (3 048 ячеек), `lay-adder` (1 485), `lay-shift-*` (≈ 2 200). Слой Форта (34,5%) больше L3 и больше всех L4+L5 вместе (14,9%).
5. **L4 и L5 малы** (4 424 и 12 322 ячейки), но размазаны: их ссылки торчат в L3/CAL/TXT/LIT/CTL (§5Б). Выделение их в «пристройки» даст заметно более простые нижние определения.
6. **Фасад Форта**: 71 генератор `gen-*` (+ 71 имя `+ dup if…`) раскладываются по группам — арифметика (21, L3), стек (10+4), память (4), управление (16), `tick/call/execute` (3), текст (8), `space*` (4), `emit key` (2), цена/хост/библиотека (5). Реестр `fc-generators` (1 905 ячеек, самое большое слово TXT) знает все языки сразу.
7. **Определение самоприменимо**: все `:`-слова нижних групп скомпилированы тем же Фортом, поэтому «образ L1» нельзя оторвать от образа L3+Форта без смены способа написания (§5А).

## 7. Вопросы автору (для 21.2)

1. Слой Форта (STK/MEM/CTL/CAL/LIT/TXT/DRV, ≈ 34% кода) — это отдельный язык между L3 и L4 («L3½») или он часть L3 / часть L5? Куда относятся `if/loop/:/variable`?
2. На каком языке пишется компилятор каждого языка? Чтобы L2→L1 вычислял `lo+n`, нужен сумматор (L3). Допустимо ли, что компилятор L2 исполняется на хосте (он не часть образа), а в образе остаётся только L1-код? Или каждый компилятор лежит в образе в своём пространстве и пишется на языке текущего или предыдущего уровня?
3. Планировщик расписаний (SCH) и кодер потока (ENC): это «компилятор L2→L1» и «L1→L0» соответственно, или они часть самого L1 (основание `lay-row` их уже содержит)?
4. Доказательство `dj-*` (9,4% кода): нужен ли оно, если L2→L1 строит непересечение по построению; или оно остаётся как проверка внешнего L1-кода (и тогда в каком языке живёт)?
5. Цена (L5p): считать только по готовым слоям (`lay-on-write`, без хуков в разборе и в `fc-plit`), чтобы нижние слова не знали о цене? Допустимо ли убрать журнал решений (`fc-log-decision`, `fc-by-execution`) из L3/CTL/CAL?
6. Где живут вывод и диагностика (`fc-reject`, `type`, `emit`): в L4 (канал хоста), и что делать с остановом, раз «ошибок нет» (18.24)? Все ли 47 проверок `fc-reject` остаются в образе?
7. `space!/@` и вычисляемая адресация (патч полей строки + сумматор): это L2 (копия с патчем) или L3? От этого зависит, ложатся ли `MEM`/`fc-access` в L2 или остаются в слое Форта.
