# Определения слов на хосте в эмуляторе: опыт (18.11)

Дата 2026-10-30, машина: Linux 6.2 x86_64, 12 ядер, во время замеров на машине шла другая работа
(load average 3,5-4). Опыт в отдельной рабочей копии, в `main` ничего не попадает. Такты детерминированы
(счётчик в эмуляторе), секунды — на одном ядре (`taskset`, процесс прибит к ядру), см. п. 5.

Мысль автора (журнал дизайна 7.2.11): эмулятор содержит определения некоторых слов языка на хосте (C), пространство
вызывает их, и они читают и пишут память пространства напрямую, а не исполняют слово копированиями.

## 1. Итог в двух строках

Два слова (`cc-row-clash?` и `fill`, вместе ~27 % тактов компилятора по замеру 18.2) перенесены на хост: такты
компиляции 37 программ упали с 3 339 млн до 2 020 млн (**1,65x**), `multiply` 1,89x, малая программа `arithmetic` 1,39x,
начало самокомпиляции (`prelude.fth` + `backend.fth`) 1,37x; поток и образ скомпилированной программы побайтно те же
(37 из 37 программ и самокомпиляция). Секунды падают в той же пропорции, что и такты (0,36 мкс за такт и до, и после).
Прирост кода эмулятора — 118 строк (9 % от 1256), из них вызов слова — 1 операция протокола.
Оценка при переносе всех дорогих групп: 2,5-3,5x по тактам на `check-kernel` и `check-self`; `make boot` (хостовый pForth)
не ускоряется вообще.

## 2. Интерфейс

### 2.1. Протокол (emulator/src/proto.def, sys_ctrl.c)

Новая операция запроса SYS `XOP(HOST, 7)`. Запись запроса та же (op 8, chan ADDR, flags 16, arg 32, off 64), поля:

| Поле | Смысл для HOST |
|---|---|
| `arg` | номер слова (таблица в эмуляторе: 0 `cc-row-clash?`, 1 `fill`; иной — статус `EINVAL`) |
| `off` | адрес блока аргументов в памяти программы («адрес Forth», байтовый), ячейки подряд; результат — в ячейку 0 поверх первого аргумента |
| `chan` | битовый адрес, с которого начинается память программы (адрес `a` лежит в бите `chan + 64*(a>>2) + 8*(a&3)`; ячейка 32 бита числовых, верхняя половина 64 битов не используется) |
| `flags` | не используется |

Исполнение: запись копируется в SYS обычным копированием (как EXEC/LONG); эмулятор в том же такте (в `service()`, до
копирований такта) вызывает определение на C, оно читает аргументы и память и пишет результат прямо в `space`; программа
читает результат с **следующего такта** (то же правило, что у ответа SYS и побочных действий EXEC). Статус — в ответе SYS:
0, `EINVAL` (неизвестное слово, запись короче положенного, начало памяти не кратно 8), `EFAULT` (адрес вне пространства;
каждый читаемый и пишемый бит проверяется на принадлежность `[0, space_nbits)`).

Определения: `hw_row_clash(org, blk)` — слово `cc-row-clash?` ( row1 row2 size -- flag ): строки по 4 ячейки
(dl dh sl sh), 2x2 пары интервалов, пересекаются, если оба непусты, пересекаются и нижние концы меньше `size`
(без знака), результат 0 / -1; `hw_fill(org, blk)` — `fill` ( addr u c -- ): байтовая заливка, байт `c` хранится
в `space` перевёрнутым по битам (числовые младшие биты первыми), одной записью байта на байт. Быстрый доступ — чтение и запись 32 бит
по границе байта через таблицу разворота битов (как «быстрый `space_get`» замера 18.2).

### 2.2. Сторона языка (language/hostwords/*.fth, primitives.fth)

* Генератор `%copy` ( dl dh sl sh -- ) (это `fc-copy-row`, генератор длинного копирования 15.2) зарегистрирован всегда, но
  в программе ядра (`fc-guard`) даёт `-13`: программа пользователя не может вызвать хост (`gen-hcopy`, 3 строки в
  `primitives.fth`, одна строка в таблице генераторов). Нужда 256: новый разряд, ничего не меняет.
* `hostwords/infra.fth` (18 строк, компилируется первой в ядре): запись запроса каждого слова постоянна (op 7, начало
  памяти ядра 3*2^29 + 2^23 = 1619001344, `arg` = номер, `off` = адрес блока `%ha`), пишется один раз `%hinit`
  (верхнеуровневый вызов, исполняется при запуске L0); вызов — `2147483648 2147483648 запись запись+152 %copy`
  (канал SYS = 2^31; `%hcall0`, `%hcall1`).
* Слово: аргументы в ячейки `%ha`, `%hcallN`, результат из `%ha`:

```forth
: cc-row-clash? ( row1 row2 -- flag ) cc-size @ %ha 8 + ! %ha 4 + ! %ha ! %hcall0 %ha @ ;
: fill ( addr u c -- ) %ha 8 + ! %ha 4 + ! %ha ! %hcall1 ;
```

### 2.3. Как собрать вариант и как выбирается путь

Хостовый pForth при сборке не должен исполнять запрос (его `fill` и `cc-row-clash?` — собственные). Поэтому
**сборка выбирает путь по тексту**: `tools/boot_host.py` загружает в pForth библиотеки (backend, compute, forthc,
primitives) без изменений, а в текст, который компилятор превращает в L0 (ядро), подставляет определения слов
через хост (`hostwords/`): `L0.host` = ядро, в котором эти два слова — вызовы эмулятора. Исходные определения
в `src/` не тронуты, они остаются эталоном (и определением для pForth, и для модели). Сборка: `python3 -B tools/boot_host.py -o L0.host
--words fill,row` (около 30-80 с на загруженной машине, как `make boot` плюс текст). Чистое решение (не опыт) — признак в самом
исходнике (например, слово с двумя определениями: «хост» и «гест») и проверка, что они совпадают.

## 3. Чем проверено, что результат тот же

Поток компилятора для программы — это образ программы в пространстве после компиляции ядром L0. Он проверен так:
эмулятор (оба варианта, одна и та же сборка счётчика) в конце печатает хеш FNV-1a двух половин пространства программы
(биты `[0, 2^29)` и `[2^30, 2^30 + 2^29)`, куда ядро пишет код и память программы) и число тактов; вывод программы сравнивается
по md5.

| Проверка | Результат |
|---|---|
| 37 программ `forthc_programs.py`: хеш образа программы и md5 вывода, до и после | 37 из 37 равны (`host-words-tools/all37-base.txt`, `all37-both.txt`) |
| `prelude.fth` + `backend.fth` + `: main ;` (начало самокомпиляции, 1,3 млрд тактов) | хеш образа равен (859346365c495fee) |
| 5 вариантов L0 (без слов хоста, fill, row, оба; базовый) на `arithmetic` и `multiply` | хеши равны |
| `make -C emulator check` (тесты эмулятора) с новой операцией | проходят |

Не проверено: `make check-self` в полном виде (часы; в нём вариант L0 компилировал бы определение языка с подстановкой, и
L1 = L0 надо проверять на тексте варианта), `check-closure` проходит, а `check-language-md` падает (сдвинулись номера строк
`primitives.fth`; `core.md` в этой копии перезаписан `check_closure.py`), тесты в `language/tests` не запускались.

## 5. Оценка на всю сборку и проверку

Что считается. `make boot` (`tools/boot.py`) исполняет определение языка на хостовом pForth, а не на эмуляторе: **выигрыша нет** (ни такта
эмулятора, ни L0 там нет; 15 с). Ускоряется всё, что исполняет L0 на эмуляторе: `check-kernel` (37 программ; 1047 с),
`check-self` (~19,4 млрд тактов, ~5700 с), пробы `check-isolation`, `check-proof` (на L0), `test_isolation`.

Метод. Доли тактов по группам слов — из замера 18.2 (п. 2 таблицы, прогон C: начало `check-self`; A: малая программа; B: `multiply`).
Проверка метода на моих данных: предсказание по долям (13,6 + 13,6 % → 1,37x) совпало с измерением (1,37x) на `prelude+backend`.

Группы, которые можно переносить так же (все — циклы по памяти, один вызов на слой или на копирование):

| Группа (18.2) | Доля, C | Что на хосте | Вызовов | Годится |
|---|---|---|---|---|
| запись слоя: `cc-encode`, `cc-numeric4`, `cc-field-check`, `cc-numeric` | 35,5 % | `cc-encode` ( rows count ): строки в байты буфера; код ошибки `-24` возвращается ячейкой и бросается словом | 1 на слой (~56 тыс. за 4 млрд тактов) | да, самое дорогое |

| `kn-put` | 9,0 % | копия байтов в половину программы с проверкой `-9` | 1 на слой | да |
| `cmove` | 4,4 % | копирование байтов вперёд по одному (перекрытие как у слова) | много, малые | частично: малые копии не окупают ~100 тактов |

Перенос четырёх первых групп и половины `cmove`: остаётся ~26 % тактов (чтение и поиск слов, словарь, служебные), плюс накладные вызовов
~3 % (оценка: ~1,2 млн вызовов на 4 млрд тактов — `fill` ~650 тыс., проверка строк ~450 тыс., запись слоя и `kn-put` по ~56 тыс., — по ~100 тактов). Верхняя оценка ускорения `check-self` и вообще
компиляции больших программ — 1/(0,26 + 0,03) = **~3,4x** (при условии, что C-слова почти ничего не стоят в тактах, что измерено для двух слов);
консервативно, если часть слов не удастся вынести целиком, — **~2,5x**.
Для `check-kernel`: малая программа (профиль A) ~65 % переносимого (`fill` 29, `kn-put` 19, запись слоя 15, остальное) — ~2,5-2,8x;
программы с `*` и `/` (профиль B, 65 % тактов `check-kernel`) ~64 % переносимого — ~2,5x (сейчас 1,9x с двумя словами). Итого
`check-kernel`: **~2,2-2,7x**, то есть ~1050 с -> ~400-480 с (на нынешнем эмуляторе, 296 нс на такт; с быстрым `space_get` из 18.2 — ещё в ~2 раза: эти две правки не зависят друг от друга).
`check-self`: ~5700 с -> ~1700-2300 с. Это оценки, а не измерения: полный перенос не делался.

## 7. Что усложнилось и проблемы

1. **Протокол**: одна новая операция, но с номером слова и **соглашением об адресах**: эмулятор знает, как устроена память
   компилятора («адрес Forth» -> бит: ячейка 32 бита на шаг 64, начало памяти ядра передаётся в `chan`). Смена `fc-mw`, шага ячеек или
   порядка байтов ломает C-слова молча. Контракт эмулятора придётся дополнить описанием «память программы».
2. **Два определения одного слова** (Forth в `src/` как эталон и для pForth, C в эмуляторе): их надо держать равными; проверка в опыте — совпадение
   образов 37 программ и самокомпиляции; в проекте нужен постоянный тест (каждое слово хоста против Forth-определения на случайных входах).
3. **`checked_vm1` (проверка непересечения)** видит только копии такта: запрос HOST для него — запись длиной в запись запроса; чтение и запись
   слов хоста (строки, буфер, блок аргументов) в проверке **не видны**, она не поймает копию того же такта, пишущую в то же место.
   Нужно, чтобы слово хоста объявляло свой след (список интервалов), и проверка добавляла их к непересечению. Эмулятор и правило
   «все интервалы такта попарно не пересекаются» сейчас на это не рассчитаны.
4. **Изоляция**: пространство и так не изолирует ядро от своего же эмулятора; изоляция программы от ядра держится на генераторах
   (`fc-guard`): `%copy` и значит вызов хоста недоступны программе (`-13`). Слово на C должно проверять каждый адрес (в опыте — бит в `[0,space_nbits)`,
   чтение и запись), иначе ошибка ядра — обрушение эмулятора; проверки «адрес внутри половины ядра» (как у `space!` в программе) не делаются.
5. **Цена и время слова** (13.4, `price`, `cost`): слово через хост — одно копирование 152 бит, а работает в тысячи раз дольше; счётчики копирований, бит, слоёв
   перестают отражать работу. Нужно правило цены для слов хоста (объявленная цена или время хоста, как у `host` в 15.3).
6. **Ошибки**: C-слово не может бросить исключение; `cc-encode` (`-24`) и `kn-put` (`-9`) возвращают код в ячейке, слово бросает; в опыте этого нет.
7. **Результат — с следующего такта**: слово языка должно разделить вызов и чтение слоем; в опыте это обеспечивают слои `fc-check` у `@` после `%copy`.
   Планировщик слоёв не знает про зависимость записи блока аргументов -> вызов -> чтения (сейчас вызов — отдельные слои `fc-copy-row`, не переупорядочиваются).
8. **Самосборка**: L1 = L0 теперь только на тексте варианта (подстановка идёт в `boot_host.py`, а не в исходниках), надо дать исходникам
   честный признак; `check-language-md` (записи `файл:строка` определений) падает при любом сдвиге строк.
9. **Воспроизводимость** `space`: определение слова «пространство» (`make space`, 15.4) — тексты эмулятора; слова хоста становятся его частью и
   вместе с языком определяют ядро. Замена пространства другим эмулятором без этих слов даст L0, который не запустится (запрос HOST не поймут).

## 8. Рекомендация

Мысль удачна: два слова из ~27 % дали 1,65x на всех программах (1,89x у `multiply`), выигрыш в секундах равен выигрышу в тактах, цена вызова
~100 тактов, 118 строк эмулятора. Предлагаю принять «определения на хосте» как понятие слова «эмулятор» при условиях: (а) переносить слова, которые
крутят цикл по памяти и вызываются нечасто (запись слоя, `fill`, `kn-put`, проверка пересечения целого слоя), и не переносить мелкие (`+!`, малые `cmove`);
(б) Forth-определение остаётся эталоном и проверяется против C постоянным тестом; (в) дописать в контракт: память программы, объявление следа
слова и цену слова, расширить `checked_vm1`. Следующий шаг пункта (ускорять слова хоста, не увеличивая код эмулятора): общий набор операций над
памятью (`fill`/`cmove`/сравнение/свёртка) вместо отдельной функции на слово, либо хосткод, который готовит кросскомпилятор и отдаёт эмулятору
(вариант 7.2.11): вызов уже дешёвый (~100 тактов против 2,1 мс у `host`), основная работа — безопасность хосткода и «след» для проверки пересечений.

## 9. Как повторить

Код опыта (в `main` не внесён) — `host-words-tools/host-words.patch` от коммита `7abcf70` (`patch -p1` в корне копии этого коммита): `emulator/src/{proto.def,sys_ctrl.c}`, `language/src/primitives.fth`, `language/hostwords/`, `language/tools/boot_host.py`;
`docs/measurements/host-words-tools/` — счётчик тактов и хеша образа (`buildemu.sh SRC OUT`), `bench.py CPU EMU L0 PROG`, `all37.py CPU EMU L0 TAG`,
таблицы 37 программ. Базовый L0 — `make -C language boot`; вариант — `boot_host.py --words fill,row`. Входы: L0 + текст программы + `\0` на stdin эмулятора
с ключами `-s 2147483648 -p 8`, как в `check_kernel.py`; сборки счётчика: `HW_TICKS=1` печатает на stderr число тактов и хеш образа программы.
