## 2. Группы: как избавиться

А (-8, 26 мест) — «ёмкость с запасом по размеру входа». Все пределы (max-words, nctl, ct, ring, cdepth, nhost,
ninit, 64-кэш) — константы. Построением: вывести из длины входа fc-tlen (слов ≤ tlen/2, имён ≤ tlen, ссылок ≤
с запасом k*tlen) и выделять таблицы по ней; тогда переполнение невозможно — но только для динамических таблиц.
Жёсткие малые пределы (nctl=32, nct=64, cdepth=16, nhost=16, ninit=64, кэш 64, tl 255) — это ограничения языка:
либо сделать запас по входу (nctl≤tlen), либо это ошибка ввода (вложенность >32) — сообщить и выйти. Дольше всего
дорогие: ёмкости ebits/rbits (число слов ограничено шириной ссылки: 2^ebits) — зависят от формата ссылки, это
граница модели; невозможной построением не сделать, не меняя формат (новый механизм = размер ссылки по входу,
пометка: меняет L0/такты). Оценка: ~18 мест устраняются запасом, ~8 — ввод пользователя (сообщить).

Б (-24, 9) — параметры сборки константны: проверять не нужно, если они проверены при проектировании (тесты).
Можно убрать совсем: 93-99,32 (проверки аргументов вызывающего); 125,177 — внутренние инварианты, убрать или
заменить `assert` внешним тестом (тест, не проверка при исполнении). Значением вернуть нечего.

В (-9, 6) — доказательство. 63/64/173: по построению (раскладка не может пересечься) — проверка избыточна, если
раскладчик корректен; но она и есть «доказатель» изоляции (dj-prove) — по решению автора проверка — построение.
kernel.fth:21-23: dj-prove возвращает флаг; вернуть значением: kn-compile возвращает флаг, main при 0 печатает
«error -9» и выходит (без throw). Это «значение + сообщение и выход».

Г/Д/Е (-13,-22,-16 — 24 места) — ошибки текста программы. Устранить построением нельзя (ввод пользователя); можно
только сообщить. Замена throw: слово печатает «error N at WORD» и завершает (halt/ выход из ядра), без возврата;
никакого catch не нужно, поскольку после сообщения программа не продолжается. Стоимость — слово `kn-fail`
(печать + выход); в самосборке (pForth) — то же через `bye`. Оно не возвращается, значит места вызова
структурно не меняются (`if kn-fail then`).

Ж (alloc/free, 22) — убрать динамику: статические буферы нужного размера (ядро — `create`/`allot`; на
хосте — `here`-область). Размер по входу (см. А). После этого `allocate/free throw` исчезают.

З (catch ядра) заменяется тем, что каждое место ошибки само печатает сообщение и выходит (kn-fail), а kn-compile
при успехе возвращает управление main: `kn-compile lay-start-cell @ execute`. Слово fc-tok/fc-tl («последнее
прочитанное слово») для сообщения остаётся.

## 3. Слова языка throw/catch (группа И): что сломается

Это не ошибки компилятора, а конструкции языка; убрать их — это изменение языка (и док. language.md, строки
23, 3210-3330, 4816-5046).
- Программы check-programs (37): `catch` (имя 'catch' в check-programs.json; его же используют faults, где
  `['] z catch` ловит деление на 0, и uncaught-zero (деление на 0 без catch завершает программу без вывода)).
  Итого затронуты 3 из 37: catch, faults, uncaught-zero (последняя использует поведение «бросок -10 вне catch»,
  не слово).
- Тесты: tests/test_disjoint.py (ожидает отказ для 'calls','catch','positions'; строка 60 программа с catch/
  throw), test_isolation.py:118 ('catch of the kernel'), test_proof.py:18,90 ('реестр 32 слов, 33-е бросает -8'
  через catch), test_word.py:50,71, test_literals.py:44,71 (`['] fc-go catch ?dup ...` — вызывают КОМПИЛЯТОР
  под catch; зависят от throw/catch в самом компиляторе!), test_closure.py:19 (список слов), tests/test_user_programs.py:54
  (`gen-cells ... -13 throw` — искусственный провал).
- Скомпилированный код: рамка catch старта (fc-push-frame) и fc-thrower; если убрать — деление на 0 должно
  завершать программу иначе (значением: результат 0? — нужно решение; вернуть код через стек — изменение
  семантики `/`; завершить — новый механизм «трап»). Помечено: это новый механизм.
- Тесты проверяют сообщения «error N at WORD» программы ядра и -8 (test_proof); их придётся переписать на «вывод
  и выход» (код выхода/вывод), поскольку throw/catch в них — средство проверки.

## 4. Варианты

В1. Минимальный: убрать только `catch` ядра и все `throw` компилятора (87 бросков + 1 catch, ~35 мест правки А/Б/В/
Г/Д/Е с kn-fail, 22 alloc → статика), оставить слова языка throw/catch. Объём: средний (~100 строк в 5 файлах +
~7 тестов: test_word, test_literals, test_proof, test_user_programs). L0/такты: компилятор растёт ~0; L1=L0
пересчитать; скомпилированные программы не меняются (такты те же). Риск: тесты, вызывающие fc-go под catch,
надо переделать на запуск с выводом; нельзя подменить catch в pForth-загрузке без bye.

В2. В1 + убрать слова языка throw/catch и деление-на-0 по броску. Объём: +fc-throw, fc-catch, fc-push-frame,
fc-build-thrower, gen-throw/gen-catch, fc-handler/fc-thrower и ветка в fc-build-div, рамка старта; доки
language.md (~10 разделов), 3 программы и 5 тестов. Деление на 0 надо определить (новый механизм трапа либо
значение, напр. результат 0 — решение автора). L0: код уменьшится (~сотни слоёв), такты: убираются запись
рамки и проверки броска, оценка — минус несколько тактов на catch, на / и mod — без изменений при результате 0.
Риск: наибольший (смена языка), L0-таблицы/размеры ebits/rbits меняются.

В3. Только проверки по построению: убрать группы А/Б/В/Ж (ёмкость по входу, статические буферы, флаги), а
Г/Д/Е оставить как `throw`, пока catch ядра остаётся. Это не выполняет 18.21 (в src остаются throw/catch).

Рекомендация: В1 в два шага: (1) Ж и А/Б/В — запасом по входу, статикой, значением вместо -9; (2) Г/Д/Е —
kn-fail «сообщить и выйти», catch ядра удалить; затем отдельным пунктом решить В2 (слова языка), поскольку
18.21 требует «нет throw/catch в language/src», то есть и gen-throw/gen-catch — иначе проверка пункта не
проходит. Поэтому в итоге нужен В2; В1 — безопасная первая часть.
