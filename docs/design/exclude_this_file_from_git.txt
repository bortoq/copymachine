>>      "литерал" — слово, превращающее текст из канала в биты; запись чисел —
>>      заменяемое определение слова "литерал". Мнение автора: всё надо
>>      перенести в язык, иначе он не будет полным.
>> 2.7. Способы проверки — определения слова проверки, заменяемы. [ПРИНЯТО]
>>      Сейчас не выбираем; кандидаты:
>> 2.7.1. полная таблица (малые слова);
>> 2.7.2. параметрические слова: функция для любой ширины n одним правилом;
>>      исчерпывающе проверяется при малых n, большие n порождаются тем же
>>      правилом. Полностью достоверная программа из полностью достоверных
>>      слов; дальше её можно только удешевлять. [ПРИНЯТО 2026-10-27]
>>      Большие функции (например, 64-битное сложение) доказываются не
>>      перебором, а построением из слов, доказанных перебором, по правилу с
>>      известным доказательством (можно брать уже имеющиеся доказательства
>>      алгоритмов). Из языка выделяются полностью доказанные слова;
>>      определение языка пишется на них.
>> 2.7.3. символьное исполнение (BDD — граф решений по битам; у функции одна
>>      сокращённая запись, равенство определений = равенство узлов) — как
>>      программа на language в гесте. Мало для сложения, логики, сравнений;
>>      для умножения/деления — через 2.7.2. Прототип вне геста и замеры —
>>      docs/research/symbolic.md;
>> 2.7.4. хеш полной таблицы: экономит хранение, но не время проверки.
>> 2.8. Определение языка. [ПРИНЯТО]
>> 2.8.1. Все определения языка даны файлом language.md и кодом; вместе они и
>>      есть определение языка (docs/dictionary.md переименовать в
>>      language.md; термины проекта, не относящиеся к языку, — решить, куда
>>      переносить). Запись понятия: текст для пользователя + ссылка на код
>>      слова + артефакт (таблица или способ проверки). Нормативны код и
>>      артефакт; текст их объясняет.
>> 2.8.1.1. [ПРИНЯТО] language.md — определение языка на русском (потом —
>>      перевод на простой английский); синхронизирован с ядром языка:
>>      запись на каждое слово ядра, ссылка на код с хешем определения,
>>      расхождение — ошибка проверки.
>> 2.8.2. Определение языка предъявляется пользователю: он лично видит, что
>>      язык — то, чем заявлен, и соглашается использовать ВС (лицензия, 1.4).
>>      Дальнейшие понятия пользователь передаёт в запросах; принимает их
>>      язык способом, зафиксированным в определении языка (2.2). ВС проводит вычисление
>>      как доказательство с известной пользователю точностью.
>> 2.8.3. ВС публикуется, когда язык рабочий: содержит свой эмулятор как своё
>>      слово и все проверки, подтверждающие, что язык — язык, действия в гесте
>>      — вычисления и т.д. До этого ВС пишется и тестируется до рабочего
>>      состояния. Поэтому эталонные артефакты первых определений проверены
>>      до публикации.
>> 2.9. Слова пользователя. [ОБСУЖДАЕТСЯ] Вопросы автора: как пользователь
>>      задаёт новые слова; как язык решает, добавлять ли определение из
>>      запроса; недоказанные слова придётся разрешить; как хранить
>>      доказательства, если таблица аргументов и результатов больше любого
>>      доступного пространства.
>>      [ПРЕДЛОЖЕНИЕ]
>> 2.9.1. Пользователь передаёт в запросе текст программы: определения и то,
>>      что вычислить. Язык компилирует их в пространство программы
>>      (изолированное от ядра, 1.1) — это слова программы, ещё не слова
>>      языка. Определение пользователя и есть смысл его нового понятия:
>>      эталон для будущих кандидатов — его поведение.
>> 2.9.2. Слово программы становится словом языка (ядра) по тому же правилу
>>      цены (1.5): если хранение определения в ядре (размер входит в цену,
>>      2.4.1) дешевле, чем его повторная компиляция и исполнение в запросах.
>>      Новое понятие сравнивать не с чем — оно принимается недоказанным, с
>>      точностью по полноте проверок (2.3); недоказанное исполняется со
>>      стоп-словом (1.8). Определение пользователя для уже существующего
>>      понятия — кандидат (2.2).
>> 2.9.3. Доказательство не хранится таблицей. Самое компактное хранение
>>      таблицы — само определение: прежние определения остаются в стеке
>>      определений (2.2.4), и их значение на любом аргументе можно вычислить
>>      заново. Храним: определение; описание проверенного множества
>>      аргументов (например, "все n-битные при n<=8", "k наборов из
>>      запросов"); способ проверки (перебор, сведение к предыдущей версии
>>      языка — цепочка использованных равенств, BDD, правило 2.7.2). Полная
>>      таблица хранится только для малых слов (2.1.4).
>> 2.10. Ядро языка и бут. [ПРИНЯТО]
>> 2.10.1. Из языка выделяется ядро языка — механизмы, которые не выражаются
>>      другими словами.
>> 2.10.2. Определение языка пишется словами ядра языка.
>> 2.10.3. Бут — механизм компиляции языка в копикод из определения языка.
>> 2.10.4. Программы пользователя — слова, определения которых не дорожают
>>      при каждой перекомпиляции языка.
>>      [ПРЕДЛОЖЕНИЕ] Механизм 2.10.4: при перекомпиляции языка программы
>>      пользователя перекомпилируются; новый код принимается, если его цена
>>      не выше, иначе остаётся прежний (стек определений, 2.2.4).
>> 2.10.5. Что уже есть (факт): ядро K — около 1100 строк Forth (prelude,
>>      backend, compute, forthc, main, kernel); исходник компилируется в
>>      индексный код и воспроизводит себя (K1 == K0). Генераторы копикода
>>      (cc-copy, cc-layer, cc-table и др., backend.fth, compute.fth) — уже
>>      слова Forth. Но примитивы языка (DUP, +, @, IF, DO, EXECUTE, ...)
>>      заданы 94 ветвями по имени внутри компилятора (fc-is?, forthc.fth) и
>>      повторены в model.py — их нельзя заменить. forthc.fth исполняется и
>>      32-битным pForth на хосте (поток равен потоку модели, секунды), и
>>      самим ядром в гесте (пересборка K1 — 84 мин).
>> 2.10.6. [ПРИНЯТО] Ядро языка — слова языка, использованные в
>>      определении языка; определение языка не содержит ничего, кроме слов
>>      языка (замкнуто: каждое использованное слово в нём же определено).
>>      Ядро не объявляется, а вычисляется по графу определения. Для этого
>>      в язык добавляются: литералы как полуинтервалы (позиции с постоянными
>>      битами), цифры — синонимы некоторых литералов, числа, мелкие
>>      механизмы из копирований и, возможно, многое другое. Основание —
>>      слова-копирования (2.1.1): определение инструкции — она сама.
>>      Компиляция — преобразование определения на языке в определение на
>>      инструкциях пространства.
>> 2.10.7. [ПРЕДЛОЖЕНИЕ] Бут без model.py: model.py — механизм вне геста
>>      (2.6.6) и требует повторять каждое слово-генератор на Python. Первый
>>      K0 строит forthc.fth на хостовом pForth или прежний K в гесте; дальше
>>      язык компилирует себя сам. Проверка перекомпиляции — артефакты: все
>>      программы тестов выдают то же, что прежде, и язык воспроизводит себя.
>> 2.11. Механизмы слова: цена, тип адресации, доказательство. [ПРИНЯТО]
>> 2.11.1. К механизму "слово языка" добавляются механизмы: цена; тип
>>      адресации — слово может исполняться в копипространстве, в
>>      индекспространстве и в хост пространстве (каким бы оно ни было);
>>      механизм доказательства.
>> 2.11.2. Экономно: для доказанных слов механизм доказательства — функция из
>>      таблицы с одним однобитным значением.
>> 2.11.3. [ПРИНЯТО] Экономия через общие слова: таблица "доказано" —
>>      одно слово на весь язык, доказанные слова ссылаются на него (цена —
>>      одна ссылка). У недоказанных — описание проверенного множества и
>>      способ (2.9.3). Тип адресации — свойство определения, а не понятия:
>>      у понятия может быть по определению на каждый тип пространства, из
>>      них выбирается самое дешёвое (1.5).
>> 2.11.4. [ПРИНЯТО 2026-10-27] Тип адресации — номер платформы: позиция
>>      таблицы "платформа", которой соответствует пространство, где
>>      определение исполняется и проверяется, и способ запуска там. Язык
>>      содержит слова, превращающие любое определение в определение,
>>      готовое к исполнению на хосте.
>> 2.11.5. [ПРИНЯТО 2026-10-27] Время двух определений равно, если разница
>>      меньше погрешности измерения на платформе (повторные запуски).
>>
>> 3. Эмулятор и хост.
>> 3.1. [ПРИНЯТО] Эмулятор — исполнитель гест пространства плюс хост
>>      пространство, управляемое программами на language из геста.
>>      [ПРИНЯТО 2026-10-27] Пространство — слово языка: понятие
>>      "пространство", определение — эмулятор, в основном слова с
>>      определениями, исполняемыми на хосте. Логика хоста считается в
>>      гесте: решение о любом действии на хосте принимает копикод геста, хост
>>      выполняет только само неделимое действие. Эмулятор становится
>>      универсальной программой: управляя им из геста, можно выполнить на
>>      хосте что угодно; внешняя граница — права пользователя ОС.
>> 3.2. Хост пространство. [ПРЕДЛОЖЕНИЕ]
>> 3.2.1. Хост пространство — виртуальная память процесса эмулятора
>>      (позиция = 8 * адрес; до 2^47 байт, поле инструкции >= 51 бит,
>>      bitcopy поддерживает до 64). Гест — диапазон внутри неё. Указатели,
>>      которые возвращают ОС и библиотеки, сразу являются позициями.
>> 3.2.2. Устройства процесс видит только через ОС: файлы /dev, /sys, /proc,
>>      системные вызовы, библиотеки. Память устройства, отображённая mmap
>>      (буфер GPU, кадровый буфер, регистры PCI через VFIO/UIO), и файлы,
>>      отображённые mmap, — обычные позиции: чтение и запись — копирование.
>>      Потоки (терминал, канал ОС) позиций не имеют — окно фиксированной
>>      длины.
>> 3.2.3. Адресация позиционная. Ассоциативная (по имени, пути) — слово языка
>>      поверх позиций, значит заменяема.
>> 3.2.4. Только bitcopy: сетевой вариант (3.8) хост пространство не
>>      поддерживает.
>> 3.3. Протокол хост-гест. [ПРИНЯТО] Язык содержит протокол общения хоста
>>      и геста (слова языка, заменяемы). Протокол уже есть — SYS
>>      (emulator/src/proto.def), но сделан по-старому: несколько адресуемых
>>      действий (CLOSE, SEEK, FSTAT, IOCTL, EXEC, каналы S..S+5) вместо
>>      одного — длинного копирования в позиции хост пространства. Задача —
>>      переопределить протокол на длинном копировании: "всегда успешное
>>      чтение или канала нет"; статус, EOF, число переданных бит, причина
>>      ошибки — данные в позициях хоста, обновляемые на границе такта.
>>      Сейчас (факт): канал — вырожденный операнд [C,C], C>=S, длину задаёт
>>      буфер. Места использования SYS — docs/research/sys-usage.md.
>>      [ПРИНЯТО 2026-10-27] Берётся имеющийся протокол SYS и переделывается
>>      под новое определение языка: действия старого протокола получают
>>      обёртку, эмулирующую длинное копирование. Длинное копирование —
>>      копирование в удалённое пространство: изолированное от данного и с
>>      другой адресацией.
>> 3.4. Функции хоста. [ПРИНЯТО, кроме помеченного]
>> 3.4.1. Интерфейс из геста один: скопировать значения в нужные позиции хоста
>>      (процессор и часть остального хост пространства). На стороне хоста
>>      механизмов исполнения может быть несколько.
>> 3.4.2. Гест не знает архитектур и платформ: передаёт имя функции и
>>      аргументы, хост исполняет. Функция указывается именем при каждом вызове
>>      (как проще); связывание имени с позицией вызова — позже, как более
>>      дешёвое определение. Протокол — слова языка, переопределяем (в том
>>      числе позже — на машинный код из геста).
>> 3.4.3. Для геста функция хоста — таблица, содержимое которой вычисляет
>>      хост: аргумент копируется в позиции, результат забирается на следующем
>>      такте (как поиск по таблице с вычисленным индексом). Это определение
>>      понятия, как любое другое: используется, если дешевле (1.5).
>> 3.4.4. [ПРЕДЛОЖЕНИЕ] Долгие и блокирующие вызовы — асинхронно, готовность —
>>      позиция-флаг; для ввода/вывода ОС даёт такой интерфейс в памяти —
>>      io_uring. GPU — через библиотеку (CUDA driver API / Vulkan); ядро GPU —
>>      определение понятия; слой копирований с непересекающимися
>>      интервалами параллелен по данным, поэтому определение слова
>>      "эмулятор" — кандидат на исполнение на GPU.
>> 3.4.5. Накладные расходы: запуск программы хоста — миллисекунды. Небольшие
>>      функции — в эмуляторе: гест переписывает и пересобирает эмулятор,
>>      добавляя функцию и получая к ней быстрый доступ (3.5). Улучшать язык
>>      можно, улучшая эмулятор.
>> 3.5. Замена эмулятора. [ПРИНЯТО]
>> 3.5.1. Гест строит код нового эмулятора, поднимает на нём новое
>>      пространство и вычисляет в нём язык, использованный для создания
>>      нового эмулятора; значение должно совпасть со значением в
>>      пространстве, инициировавшем замену (1.7 для слова "эмулятор").
>> 3.5.2. Идея автора: гест через запуск на хосте создаёт новое пространство
>>      нужного размера, копирует себя в него через каналы, продолжает работу
>>      там и завершает старое. SYS EXEC для запуска на хосте уже есть.
>> 3.6. Позиции, через которые значения приходят извне (каналы ввода, функции
>>      хоста с недетерминированным результатом), автор думает считать
>>      управляющими каналами; это требует слов "управление", "пользователь".
>>      [ОТЛОЖЕНО] Остальная часть языка делается без них. Их значения
>>      считаются битами, прочитанными через канал (аргументами, 2.1.4); в
>>      замене эмулятора (3.5.1) сравниваются только значения, не зависящие от
>>      них.
>> 3.7. Изоляция (1.3): цепочка механизмов от логики до копирования
>>      непересекающихся полуинтервалов в одном слое (факт):
>> 3.7.1. сетевой вариант доказывает, что копирование непересекающихся
>>      полуинтервалов слоя реализуемо без сложения адресов (3.8);
>> 3.7.2. непересечение обеспечивает гест, а не хостовая часть эмулятора:
>>      планировщик в гесте (forthc.fth, "straight-line scheduler", fc-place и
>>      cc-fits? из backend.fth) кладёт копирование в слой, только если оно ни
>>      с чем не пересекается; таблица, адрес чтения которой вычисляется при
>>      исполнении, читается не более одного раза за слой (fc-has?). Хостовые
>>      планировщик и оптимизатор (Python, copycode.vm1) делают то же для
>>      старых путей;
>> 3.7.3. checked-emulator (только в тестах) дополнительно проверяет каждый
>>      такт при исполнении;
>> 3.7.4. изоляция ядра от программ пользователя в K: @ ! C@ C! проверяют
>>      адрес (THROW -9), приёмник кода программы пишет только в её половину
>>      пространства (kn-put).
>> 3.7.5. Не сделано: слово, доказывающее непересечение позиций программы
>>      (сейчас непересечение обеспечено построением кода). По коду (не
>>      проверено запуском): SPACE!/SPACEC! — примитивы без проверки половины
>>      (forthc.fth:729, 775), и EXECUTE переходит по любому числу — программа
>>      пользователя, похоже, может писать в ядро и исполнять его код с
>>      середины, что нарушает 1.1.
>> 3.7.6. Хост и гест — части одного целого (0.9); весь контроль — в гесте,
>>      изоляцию может нарушить только копикод геста, а он проверяется.
>>      Хосткод (код в инструкциях процессора хоста) — не копикод: схему его
>>      изоляции автор изложит позже. [ПРЕДЛОЖЕНИЕ] хосткод в отдельном
>>      процессе, которому ОС отображает только его позиции.
>> 3.8. Размеры. Размер геста задаётся при запуске (-s). Сетевой вариант —
>>      модель аппаратного механизма копирования (сравнения и перенос ключей
>>      через сортирующую сеть); ключи 16-битные, поэтому S<=65520, P<=128.
>>      Ограничение не принципиальное: ширина ключа может быть
>>      bit_length(S); но сеть растёт как N log^2 N и программно для больших S

>>      bitcopy — S любой, до памяти хоста.
